# 代码分层约定

业务模块参考 `src/admin/` 的组织方式：

```text
src/<业务模块>/
  dto/                       每个请求对象独立文件，保留校验与转换装饰器
  <模块>.controller.ts       路由、请求参数、鉴权入口和服务调用
  <模块>.service.ts          业务校验、权限范围、状态流转和响应转换
  <模块>.repository.ts       数据查询、写入与事务入口
  <模块>.module.ts           Nest 控制器、Provider 和跨模块依赖注册
```

控制器不访问数据库；业务服务通过本模块 Repository 读写数据。跨模块业务调用继续使用对应 Service。共享鉴权、拦截器和 Prisma 连接生命周期保留在基础设施目录中。

Repository 的查询方法保留 Prisma 参数及返回值的泛型推导，Service 负责构造业务筛选条件。需要跨查询保持一致性的操作由 Service 编排事务，将事务客户端传入 Repository；不传入时使用模块注入的数据库连接。Repository 查询直接返回 PrismaPromise，不增加 `async` 包装，以保持数组事务的延迟执行。事务隔离级别、版本检查、幂等键、行锁和重试策略沿用现有业务实现。

DTO 按类放入 `dto/`。校验辅助函数放入模块工具文件；用户鉴权的 Guard、请求类型和测试手机号配置分别独立存放。订单的用户端与后台管理端分别组织控制器、服务及 Repository。

方法前使用中文说明职责，复杂流程在关键步骤写编号注释，解释权限、幂等、库存、金额和状态转换的业务约束。装饰器独占一行，统一使用项目 Prettier 配置。

原有 `*.dto.ts`、`user-auth.ts` 和 `orders-management.ts` 入口保留兼容导出；项目内部直接引用对应实现文件。开发检查脚本的手动服务构造已同步注入 Repository。

本次重构不修改数据库结构、接口路径、请求校验规则、响应字段或业务规则。验证使用现有业务测试、应用模块依赖装配测试和 TypeScript/Nest 构建，不依赖真实数据库写入。
